# Keeping a project up to date: `forge update`

A project generated by Forge is a snapshot. Templates improve, security pipelines get refreshed pins, a better Dockerfile ships. `forge update` brings your project forward to what the **installed Forge** would generate today, **without losing anything you changed**.

> `forge update` updates *your project*. It does not update the Forge CLI itself. For that, use `npm update -g` (or however you installed it).

```sh
forge update --dry-run          # what would change?
forge update --dry-run --diff   # ...line by line
forge update                    # do it
forge update --check            # CI: exit 8 if the project is behind
```

## What it does

For every file, Forge compares three things:

- **recorded**: what Forge wrote last time (kept as a hash in `.forge/state.json`)
- **yours**: what is on disk now
- **template**: what this Forge would write today

Whether *you* changed a file and whether *the template* changed it are independent questions. That is what makes it safe:

| You changed it? | Template changed it? | Result |
|---|---|---|
| no | no | nothing to do |
| no | **yes** | **updated** (a backup is kept) |
| **yes** | no | **kept**: your edit stands, no noise |
| **yes** | **yes** | **conflict**: nothing is overwritten (see below) |
| you made the same change | yes | converged: recorded as up to date |
| you deleted it | no | left deleted |
| you deleted it | **yes** | conflict (Forge never silently recreates a file you removed) |
| not generated by Forge, but a file is in the way | new | conflict |
| untouched, but the template no longer produces it | | **orphan**: reported; removed only with `--prune` |
| you edited it, and the template no longer produces it | | **yours now**: never deleted, no longer tracked |

Files Forge only creates once (such as a `LICENSE` marked create-only by a template) are never updated afterwards. Files merged into shared content (`.gitignore`, `package.json`, `.gitlab-ci.yml`) are merged again, which adds anything new but never removes lines you or upstream already have.

## Updates are driven by content, not version numbers

Forge compares what it would write against what it wrote. A new Forge release can refresh pinned action SHAs, or fix a generator, without any template version changing, and `forge update` picks that up. Version numbers are shown for information and used for exactly one thing: refusing a downgrade.

## Conflicts

When you and the template both changed a file, the default is to **stop and change nothing** (exit code 4) and say why:

```
error: Refusing to overwrite 1 path:
  README.md: you changed it and the template changed it
hint: See the differences with "forge update --dry-run --diff". Then merge by hand, or use
      --partial (apply the rest) or --force (take the template's version; yours is backed up).
```

| Option | What happens |
|---|---|
| `--dry-run --diff` | Shows a unified diff of **your file against what the template would write**, for each conflict and each update. |
| `--partial` | Applies everything that is not a conflict. Conflicted files are left byte-for-byte as they are. Exits 4 so CI notices that conflicts remain. |
| `--force` | Takes the template's version for conflicts. Yours is saved under `.forge/backup/`. Symbolic links and directories are never overridden. |

After `--partial`, a conflicted file is still reported next time. Merge it by hand so it matches the template and it is recorded as converged; or take the template's version with `--force`.

Forge does not merge the *contents* of a file that both sides changed. It tells you precisely which files collide and shows the difference; combining them is your call.

## Orphans and `--prune`

If the template stops producing a file (or you change an answer so it no longer applies), Forge **reports** it but does not delete it. `--prune` removes it, only if you never edited it, with a backup, and the deletion is rolled back if anything fails. A file you edited is never deleted, even with `--prune --force`. Emptied directories are left in place.

## Answers

Answers you gave to `forge new` and `forge add` (except secrets) are remembered and reused.

- A **new question** added upstream: with `--yes` its default is used, in a terminal you are asked, otherwise Forge stops and names the flag (`--answer key=value`).
- A **removed question**, or a remembered answer that is no longer valid (for example a choice that no longer exists), is dropped and reported. Forge never trusts a stale value.
- **Secret** answers are never stored, so you pass them again.
- `--answer key=value` changes a decision, and is remembered. For example `forge update --answer docker=false` makes the Dockerfile an orphan.

## Safety guarantees

Everything Forge guarantees elsewhere applies: updates are **atomic** (a failure or Ctrl-C at any step restores the exact previous tree, including deletions), **idempotent** (a second `forge update` changes nothing), **contained** (nothing outside the project, no symlinks followed) and **non-destructive** (a file you changed is never overwritten without `--force`, which keeps a backup). Forge warns, but does not stop you, when the git working tree has uncommitted changes.

A tested invariant: for a project you never touched, `forge update` produces the same files as generating a fresh project with the new version.

## Exit codes

| Code | Meaning |
|---|---|
| 0 | Updated, or already up to date |
| 3 | Invalid answers or state, or the update would downgrade a template |
| 4 | Conflicts (refused, or `--partial` left some) |
| 5 | The template or feature the project came from is not installed |
| 8 | `--check`: the project is behind |

## Limits

- Projects must have `.forge/state.json`. To bring an existing repository under Forge, run `forge add`.
- Content-level merging of a file changed on both sides is not supported yet.
- Templates are data, so a template cannot run migration code: a rename shows up as an orphan plus a new file.
- Lines removed upstream from merged shared files (`.gitignore`, etc.) are not removed from your copy.
